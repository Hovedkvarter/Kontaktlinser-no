Source checked: 2026-10-29. Excerpt revision: CL-1.0-offline-2026-10-29.
This is a shortened, sanitized implementation aid, not the full standard,
a new decision log, an operational approval or a copy of Property evidence.
The same excerpt is kept in the three participating repositories.

## Start

Before material work, read the repository instructions and task-relevant
current decisions. Search existing Issues, PRs, runbooks and local learning
records for the same problem. State the prior learning used, exact Property
and environment, code/schema version and current authorization. Recheck dated
limitations; do not treat a historical restriction or approval as current.
Read only what the task needs.

When approved Drive access is available, retrieve the relevant current source
section; a link does not load its contents. If Drive is unavailable, report
offline mode and this excerpt's revision, use local rules and version-bound
evidence for work whose basis is established. Missing decisive evidence means
unresolved basis: hold the dependent action, never guess authorization or use
another Property's records to fill the gap. Continue independent authorized work.
On conflict, identify the sources, dates and scopes and reconcile explicitly;
do not silently replace local rules or erase history.

## Keep four statuses separate

- **OBSERVERT:** dated result, source and scope; confirmed cause and hypothesis
  are different claims.
- **VEDTATT:** explicit human-approved principle/decision, date and limits.
- **IMPLEMENTERT:** concrete commit/PR plus relevant test evidence. Operational
  verification additionally names environment, runtime/schema and actual result.
  Merged code is not proof of deployment.
- **FORSLAG/ÅPENT:** untested or unimplemented improvement tied to an existing
  Issue and acceptance criteria. It grants no decision, right or approval.

## Preserve scope

Reuse methods and authorized evidence pointers across Core, Products/Commerce,
Leads and websites. Never transfer Property data, personal data, credentials,
delegated powers, approvals or commercial/image rights between websites.
Access to one repository or document does not authorize another Property.
Keep original incidents in their existing location; promote a shared rule only
with documented applicability and exceptions. A single advertiser approval
does not cover a network; a CDN observation does not establish a universal URL
rule. Owner approval is not external licence confirmation. Preserve current
revocations and all Property, security, resource and rights gates.
Shared notes must exclude secrets, tokens, personal data and raw signed URLs;
private evidence keeps its original access and retention rules.

## Finish material work

Record in an existing Issue, PR or runbook: problem/impact, date and affected
services/Properties, observed cause and uncertainty, fix or limitation,
verifiable evidence, reuse scope/exceptions, prevention or automation,
regression coverage/missing test, follow-up owner and required approval.
Link originals rather than build another register.

Answer: what was learned and remains unknown; cause proven or assumed;
what can be prevented/automated; which existing tests cover it and which test
is missing; which standard/runbook/decision needs updating; which other scopes
have documented benefit; where the note and unimplemented follow-up live.
"No new material learning" with a reason is sufficient when true. Do not make
empty notes or rerun unchanged tests just to fill a checklist. Reuse test
evidence only while code, environment and assumptions remain unchanged.

## Source maintenance

Refresh only from the authorized source, record its revision/check date,
review the diff for scope and private data, and update this excerpt consistently
through reviewed PRs. Do not copy incident payloads or the full Drive documents.
A newer conflicting decision requires explicit reconciliation, not automatic
promotion of this excerpt.
